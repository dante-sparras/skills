# The tracker

Issues and specs live as GitHub issues. Use the `gh` CLI for issues, and T3's `pull_request_*` tools and `ci_logs` for pull requests.

`gh` infers the repo from the clone it runs in. In a fork that can be the upstream repo, so before the first `gh issue create` of a session, check the target with `gh repo view --json nameWithOwner`, and pass `--repo` when it is not the repo the user means.

## Labels

Every label is named after its role, and the `factory` skill creates them: the states `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, and `wontfix`, the categories `bug` and `enhancement`, and `spec`. [triage](../triage/SKILL.md#roles) says what each state and category means. `spec` marks a spec: the parent of tickets, not work to grab.

## Issues

- **Mark what an agent posts**: open every comment and issue an agent writes with the line `> *This was generated by AI.*`, and a blank line after it.
- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies.
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,comments`.
- **List issues**: `gh issue list --state open --limit 200 --json number,title,author,createdAt,updatedAt,labels,comments`, with `--label` and `--state` filters as needed. The default limit is 30, so always pass one. Read a body as in **Read an issue**. A list trails a new issue or a new label by some seconds, so read an issue you just changed by its number.
- **Make an issue a sub-issue of a parent**: `gh issue create --parent <parent> ...`, or `gh issue edit <parent> --add-sub-issue <child>` afterwards (`gh` 2.94+). Older `gh`: `gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>` (database id, as in **Blocking** below). Without sub-issues, put `Part of #<parent>` at the top of the child body.
- **Blocking**: GitHub's **native issue dependencies**, the canonical, UI-visible representation. Add an edge with `gh issue create --blocked-by <n>,<n> ...` or `gh issue edit <child> --add-blocked-by <blocker>` (`gh` 2.94+). Older `gh`: `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's numeric **database id** (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`, _not_ the `#number` or `node_id`). Where dependencies aren't available, fall back to a `## Blocked by` section in the child body. A ticket is unblocked when every blocker is closed.
- **Count open blockers**: `gh api repos/<owner>/<repo>/issues/<n> --jq '.issue_dependencies_summary.blocked_by // 0'` (open blockers only, 0 means startable). `gh issue view <n> --json blockedBy` also lists closed blockers, so filter it: `--jq '[.blockedBy.nodes[] | select(.state == "OPEN")] | length'`.
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Edit a comment**: `gh issue comment` prints the new comment's URL, and the number after `issuecomment-` is its id. Edit it with `gh api --method PATCH repos/<owner>/<repo>/issues/comments/<id> -f body="..."`.
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: post the explanation with `gh issue comment <number> --body "..."`, then `gh issue close <number>`. On an already-closed issue, `gh issue close --comment` drops the comment and still exits 0.

## Pull requests

Read, comment on, label, and close a PR with T3's `pull_request_*` tools. A PR takes the same labels as an issue.

- **List external PRs**: `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER","MEMBER","COLLABORATOR") | not) | {number, title, author: .user.login, author_association, labels: [.labels[].name]}'`. A PR is external when its author is not a collaborator.
- **A bare `#42`** may be either, since GitHub shares one number space across issues and PRs: resolve it with `gh pr view 42` and fall back to `gh issue view 42`.
